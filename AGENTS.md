# AGENTS.md

## О проекте

Персональное приложение для учёта и анализа финансов. Пользователь вносит доходы и расходы, распределяет их по категориям и другим параметрам, настраивает учёт и получает подробную статистику за различные периоды (месяцы, годы и т. д.). Приложение помогает понимать своё финансовое положение, видеть структуру доходов и расходов, отслеживать изменения и анализировать их причины.

## Правила работы

1. **Минимальная достаточность.** Не создавать лишнюю функциональность, файлы, абстракции, архитектурные слои и документацию без реальной необходимости. Предпочитать наиболее простое решение, которое качественно выполняет задачу.
2. **Спецификации — источник истины.** Перед выполнением задачи изучать только релевантные документы. Не загружать всю документацию без необходимости.
3. **Не додумывать требования.** Не считать собственные предположения утверждёнными решениями. Если существенное требование не определено, уточнять его, а не самостоятельно придумывать.
4. **Актуальность документации.** При изменении зафиксированных требований или решений обновлять соответствующие спецификации. Если меняется структура документации, назначение файлов или существенный контекст проекта, обязательно обновлять `AGENTS.md`. Следить, чтобы ссылки и описания документов в нём всегда оставались актуальными.
5. **Отсутствие дублирования.** Каждое требование или решение должно иметь один основной источник истины. Не дублировать подробное содержание спецификаций в других документах.
6. **Простота и качество кода.** Писать понятный, читаемый и поддерживаемый код. Не вводить усложнения и абстракции ради гипотетических будущих возможностей.
7. **Соблюдение существующих решений.** При реализации новой функциональности учитывать уже принятые технические, архитектурные и стилистические решения. Не менять их произвольно.

## Порядок выполнения задачи

### Перед реализацией

1. Изучить относящиеся к задаче требования, макеты и существующую реализацию. Определить, достаточно ли зафиксированных решений для выполнения задачи.
2. Если не определены существенные пользовательские сценарии, внешний вид или поведение интерфейса, описать проблему и варианты решения, получить решение пользователя и зафиксировать его в соответствующей спецификации. До согласования не реализовывать зависящую от него часть задачи; независимую работу продолжать.
3. Технические детали, исправление ошибок и другие вопросы, которые не меняют требования и утверждённый дизайн, решать самостоятельно.

Существенными считаются решения, которые пользователь увидит или которые изменят его действия: например, состав и расположение элементов, сценарий выбора, оформление нового типа компонента, поведение открытия и закрытия. Новый календарь или стиль попапа согласовываются; исправление сломанного клавиатурного управления в уже согласованном календаре выполняется самостоятельно.

### При работе с интерфейсом

1. Найти соответствующий компонент в `front/src/shared/ui` и посмотреть его пример на странице `/ui-kit`.
2. Если компонент не подходит или отсутствует, проверить возможности установленного UI SDK и определить, требуется ли новый общий компонент или изменение существующего.
3. Не создавать локальную замену общему компоненту на странице и не выбирать новое визуальное решение без согласования. Если для нового компонента или его существенного состояния нет утверждённого вида, предложить пользователю варианты; при необходимости подготовить визуальный прототип.
4. После согласования обновить дизайн-спецификацию, реализовать общий компонент в `shared/ui`, добавить его демонстрацию в `/ui-kit` и использовать в целевом сценарии.

### Перед завершением

1. Выполнить проверки, относящиеся к изменению, и исправить обнаруженные проблемы.
2. Для изменений интерфейса проверить в браузере затронутый пользовательский сценарий, основные состояния, клавиатурное управление и узкий экран. Сверить результат с утверждённым макетом и дизайн-спецификацией.
3. В итоговом сообщении указать результат, выполненные проверки и то, что проверить не удалось.
4. Создать отдельный коммит задачи по правилам проекта.

## Коммиты

- Каждую завершённую задачу фиксировать отдельным Git-коммитом.
- Оформлять сообщения по Conventional Commits с обязательным scope.
- Писать сообщения на английском языке.
- Примеры: `feat(transactions): add transaction filters`, `fix(categories): prevent deleting used categories`, `docs(technical): define frontend structure`.

## UI SDK

- При начальной настройке frontend, если проект поддерживает skills, добавить skill командой `npx skills add vercel-labs/ui --skill ui-sdk`.
- Перед использованием `@ui-sdk/react` следовать инструкции UI SDK, если соответствующий skill установлен, и читать `front/node_modules/@ui-sdk/react/docs/llms.txt`.
- Перед созданием нового компонента найти нужный раздел в `front/node_modules/@ui-sdk/react/docs/core.md` и прочитать связанный `rendering.md`.
- Устанавливать `@ui-sdk/react` и `@ui-sdk/core` в приложении `/front`. Если установка заблокирована политикой минимального возраста релиза, остановиться и сообщить пользователю; не менять настройки политики.
- При совместном использовании с Tailwind CSS в глобальной таблице стилей использовать порядок импорта, рекомендованный UI SDK:

  ```css
  @layer ui-sdk;
  @import "tailwindcss";
  @import "@ui-sdk/core/web.css" layer(components);
  ```

- После настройки запускать production build приложения и исправлять ошибки сборки.
