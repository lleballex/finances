# Техническая спецификация

## Технологический стек

### Frontend

- Next.js с App Router.
- TypeScript.
- Tailwind CSS.
- Zustand для клиентского состояния интерфейса. Режим учёта сохраняется на клиенте, не в базе данных.
- TanStack Query для получения, кэширования и обновления данных API.
- Axios для HTTP-запросов к backend через общий настроенный клиент.
- React Hook Form и Zod для форм и клиентской валидации.
- `@ui-sdk/react` и `@ui-sdk/core` для создания доступных интерактивных компонентов с собственным оформлением на Tailwind CSS.
- UI SDK принимается как beta-инструмент; использовать зафиксированную версию и учитывать, что его API может измениться.
- UI-компоненты должны соответствовать дизайн-решениям проекта, корректно работать на desktop-экранах, поддерживать клавиатурное управление и необходимую интерактивность. Адаптация для узких экранов отложена до отдельной итерации. Анимацию использовать там, где она предусмотрена дизайном и помогает взаимодействию.
- Не выбирать отдельные UI-библиотеки для каждой функции. Если нужного поведения нет в UI SDK, сначала изучить его документацию и согласовать альтернативу.

### Backend

- NestJS.
- TypeScript с включённым `strict` и проверкой `strictNullChecks`. Строгие проверки TypeScript не отключать.
- TypeORM.
- PostgreSQL.
- `@nestjs/swagger` и Swagger-плагин для описания API.
- `class-validator` и `class-transformer` для валидации и преобразования DTO.
- Глобальный `ValidationPipe` для входящих DTO.
- Изменения схемы базы данных выполнять миграциями. Не использовать автоматическую синхронизацию TypeORM в рабочем окружении.
- HTTP API: REST с JSON и префиксом `/api/v1`.
- API размещается на поддомене frontend: `https://api.<домен-frontend>`.

### Авторизация

- После авторизации через Яндекс ID backend выдаёт JWT приложения и передаёт его браузеру в cookie с `HttpOnly`.
- Не хранить JWT приложения в `localStorage` или `sessionStorage`.
- Cookie размещается на API-хосте и использует `HttpOnly`, `Secure` и `SameSite=Lax`.
- Axios отправляет cookie с API-запросами. Nest разрешает credentials только для точного origin frontend; запросы, изменяющие данные, дополнительно проверяют `Origin`.
- Не хранить JWT в базе данных.
- При выходе удаляется cookie в текущем браузере. Серверный отзыв JWT не выполняется; токен остаётся действительным до истечения срока действия.
- Использовать один JWT сроком действия 7 дней, без refresh-токена. Срок жизни cookie должен совпадать со сроком JWT.
- Токены не хранятся в базе данных.

### Пагинация API

- Для постраничной выдачи передавать необязательные параметры `page` и `limit`; значения по умолчанию устанавливает backend.
- Нумерация страниц начинается с 1. Значение `page` по умолчанию — `1`, значение `limit` по умолчанию — `20`.
- Ответ возвращает список в `data` и метаданные в `meta`: текущая страница, лимит и общее число записей, подходящих под фильтры.

### Инструменты разработки

- ESLint для статического анализа и проверки соглашений по коду.
- Prettier для форматирования.
- Node.js 26, выбираемый через NVM и локальные `.nvmrc` в `/front` и `/back`.
- Yarn 4; точную версию закрепить в поле `packageManager` каждого приложения.

## Архитектура и организация кода

### Frontend

Использовать организацию по функциональным областям без обязательного внедрения отдельной архитектурной методологии:

```text
/front
  src/
    app/                # маршруты, layout и композиция страниц
    features/
      auth/
      dashboard/
      transactions/
      categories/
      statistics/
    shared/
      api/              # общий HTTP-клиент и общие API-типы
      ui/               # выбранные общие UI-компоненты
      lib/              # действительно общие утилиты

/back
  src/
    modules/            # модули NestJS по функциональным областям
```

Страницы и layout размещать в `app`. Компоненты, запросы, хуки, схемы и типы размещать рядом с соответствующей функциональной областью, когда они нужны. `app` собирает страницы из компонентов функций. Серверные компоненты использовать по умолчанию, клиентские — для интерактивного поведения и клиентского состояния.

`front/src/shared/ui` содержит общие компоненты приложения, а `/ui-kit` демонстрирует их варианты и состояния. Перед добавлением общего элемента необходимо проверить существующие компоненты. Наличие компонента в коде само по себе не подтверждает, что его внешний вид и поведение согласованы; при расхождении приоритет имеют утверждённые спецификации и макеты.

Zustand использовать для состояния интерфейса, TanStack Query — для состояния данных, получаемых с backend. Не дублировать кэш серверных данных в Zustand.

### Backend

Использовать модульную архитектуру NestJS с разделением по функциональным областям, например `auth`, `users`, `categories`, `transactions`, `statistics`.

Контроллеры отвечают за HTTP-уровень, сервисы — за прикладную логику, DTO — за входные и выходные контракты. Не возвращать TypeORM-сущности напрямую в API-ответах. Не вводить общие слои, обёртки и абстракции без необходимости для текущей функциональности.

## Дизайн при реализации интерфейса

- Строго соблюдать токены, размеры, типографику, отступы и правила элементов из [спецификации дизайна](05-design.md); она является основным источником визуальных решений.
- Применять утверждённые значения последовательно для одинаковых элементов. Не вводить самостоятельно новые цвета, размеры, шрифты, начертания, отступы или другие визуальные стандарты, отсутствующие в спецификации.
- Если для задачи нужен новый токен или визуальный стандарт, до его использования согласовать его с пользователем и затем обновить спецификацию дизайна.

## Требования к коду

- Код должен быть чистым, читаемым и последовательно оформленным.
- Разделять ответственность и применять одинаковые паттерны для одинаковых задач.
- Реализовывать только необходимые для текущей задачи решения; не усложнять код ради гипотетического расширения.
- Не дублировать логику и не хранить конфигурационные значения в коде. Настройки окружения передавать через конфигурацию приложения.
- Все входные данные API валидировать DTO на backend. Клиентская валидация не заменяет серверную.
- Поддерживать единый формат кода через ESLint и Prettier.

Для изменяемого поведения выбирать проверки, соответствующие риску и сложности задачи. Автоматическими тестами покрывать существенную логику и интерактивное поведение, для которых тест помогает предотвратить регрессию. При использовании UI SDK также выполнять применимые требования установленного skill. Прохождение автоматических тестов не заменяет проверку интерфейса в браузере.
